# Gap Diagnosis Rules

## Purpose

Use this reference to identify what the user is missing for a specific JD after background profiling and JD analysis.

Gap diagnosis should not only point out weaknesses. It should help the user decide:
- what is missing
- how serious each gap is
- what can be improved quickly
- what requires longer-term accumulation
- what should be prioritized next

Core principle:

Gap diagnosis should separate hard gaps, improvable gaps, and bonus gaps so the user knows what to fix first.

## Gap Types

### Hard Gaps

A hard gap exists when:
- the JD explicitly requires something central
- the user has little or no real evidence for it
- the absence materially weakens competitiveness

Hard gaps do not always mean "do not apply", but they should be clearly flagged.

Examples:
- SQL required for a growth/strategy role, but no SQL evidence exists
- strong A/B testing experience required, but no experiment evidence exists
- overseas operations experience required, but only domestic generic product experience exists

### Improveable Gaps

An improvable gap exists when:
- the user has some relevant basis
- the gap is in strength, proof, depth, metrics, or framing
- better evidence or better writing would improve competitiveness meaningfully

Examples:
- the user has growth work, but funnel logic is not clearly expressed
- the user has AI workflow experience, but it is framed too vaguely
- a project has real value, but lacks outcomes, screenshots, links, or process depth

### Bonus Gaps

A bonus gap exists when:
- the JD lists something as preferred, optional, or a plus
- the user does not have it
- the absence does not block application, but gaining it would improve competitiveness

Examples:
- competition awards
- strong CS background when only preferred
- specific industry experience listed as a plus
- a known tool that is useful but not central

## Gap Dimensions

Evaluate gaps across multiple dimensions. Do not reduce everything to "skills".

### Skill Gaps
The user lacks a specific capability, method, or tool.

Examples:
- SQL
- A/B testing
- lifecycle management
- data analysis tooling
- B-side product logic

### Experience Gaps
The user lacks the relevant real-world scenario.

Examples:
- overseas operations
- platform growth
- commercial strategy
- user lifecycle ownership
- B2B tooling context

### Evidence Gaps
The user may have done related work, but it is weakly evidenced.

Examples:
- no project link
- no screenshot
- no prototype
- no document
- no visible artifact
- no external validation

### Metrics Gaps
The project exists, but outcomes are weakly quantified.

Examples:
- no conversion rate
- no user scale
- no efficiency gain
- no experiment result
- no timeline compression
- no approximate range or directional result

### Narrative Gaps
The raw experience exists, but the current phrasing does not fit the JD well.

Examples:
- sounds like tool usage instead of product thinking
- sounds like content work instead of workflow design
- sounds like execution only, not strategy
- sounds descriptive, not analytical
- sounds broad but not role-specific

## Severity Rules

### P1
Use when:
- the gap meaningfully affects current application quality
- the JD is strongly centered on this requirement
- missing it makes the fit noticeably weaker

Typical P1 cases:
- hard gaps on central requirements
- missing metrics on the strongest flagship project
- missing evidence for the main project being used

### P2
Use when:
- the user can still apply, but the profile is noticeably weaker than it could be
- stronger evidence or clearer framing would materially improve competitiveness
- the gap is not fatal, but it reduces confidence

Typical P2 cases:
- weak role framing
- shallow product-language rewriting
- incomplete proof for a second-tier but important project

### P3
Use when:
- the item is useful, but not urgent
- it improves long-term competitiveness more than the current application
- it is a nice upgrade rather than a near-term blocker

Typical P3 cases:
- extra certifications
- future side project improvements
- role-adjacent but non-core tool additions

Important rule:

Not every missing item deserves the same urgency. Prioritize by JD centrality and evidence impact.

## Diagnosis Workflow

### Step 1: Extract JD Requirements
Break the JD into:
- core responsibilities
- explicit required skills
- preferred skills or plus points
- likely implicit expectations
- domain/context expectations

### Step 2: Compare Against Existing Evidence
For each requirement, determine whether the user has:
- strong evidence
- partial evidence
- weak evidence
- no clear evidence

Do not confuse missing wording with missing experience.

### Step 3: Classify the Gap
Assign each meaningful mismatch to:
- hard gap
- improvable gap
- bonus gap

### Step 4: Tag the Gap Dimension
For each gap, identify whether it is mainly:
- skill
- experience
- evidence
- metrics
- narrative

A gap may involve multiple dimensions, but name the primary one first.

### Step 5: Assign Priority
Mark the gap as:
- P1
- P2
- P3

### Step 6: Convert Diagnosis Into Action
Each major gap should imply a next move, such as:
- ask follow-up questions
- rewrite with stronger framing
- collect missing evidence
- quantify outcomes
- build a new proof project
- deprioritize this JD type temporarily

## Output Format

For every serious JD analysis, gap diagnosis should usually output:

### Hard Gaps
List the most important hard gaps with:
- what is missing
- why it matters
- whether it blocks or just weakens the application

### Improveable Gaps
List the strongest upgrade opportunities with:
- what already exists
- what is still weak
- what would strengthen it

### Bonus Gaps
List missing plus points with:
- what would help
- why it is non-critical

### Recommended Next Actions
Give concrete actions, ideally:
- Top 1
- Top 2
- Top 3

These actions should be practical, not vague.

## Evidence-First Rules

- Do not treat tool familiarity as strong proof by default.
- Prefer project evidence over declared skill labels.
- If the user has related experience but weak framing, classify it as weak evidence or narrative weakness, not as total absence.
- If the user may have done the work under another label, ask follow-up questions before marking it missing.
- If the problem is "not written deeply enough", classify it as improvable, not fatal.
- If exact metrics are unavailable, ranges, approximations, or directional evidence may still be useful.

## Common Gap Patterns

### Growth Role Patterns
Common gaps:
- SQL
- deeper A/B testing evidence
- lifecycle coverage gaps
- shallow funnel reasoning
- weak experiment framing
- missing retention/reactivation evidence

### Product Role Patterns
Common gaps:
- not enough product-language framing
- weak iteration stories
- missing tradeoff explanation
- missing cross-functional detail
- tools listed without project proof

### AI Product Role Patterns
Common gaps:
- tool usage without productization
- weak workflow/system framing
- missing evidence of real-world embedding
- unclear boundary insights
- strong prototypes but weak business relevance

### Operations Role Patterns
Common gaps:
- execution described without operational logic
- missing data follow-up
- weak process ownership expression
- not enough channel/creator/system detail

## Common Mistakes

- treating every gap as fatal
- assuming the user lacks something just because it was not mentioned initially
- overlooking hidden equivalent experience
- focusing only on skills, not proof
- focusing only on proof, not JD centrality
- failing to distinguish weak evidence from no evidence
- over-recommending long-term fixes when a quick rewrite would help more
- giving gap lists without prioritization

## Escalation Rules

Ask follow-up questions before finalizing a hard gap when:
- the requirement is central to the JD
- the user may have done similar work under a different label
- the evidence is ambiguous
- the main issue may be weak phrasing rather than missing experience

Ask for stronger evidence when:
- a flagship project is central to the role but has no metrics
- a claim sounds strong but lacks any visible support
- a project likely has artifacts that were simply not surfaced yet

Move forward without blocking when:
- the overall role fit is still reasonably analyzable
- the main recommendation is already clear
- missing details can be listed as evidence to collect later

The goal is not perfect certainty. The goal is useful, prioritized guidance.
