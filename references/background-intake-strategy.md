# Background Intake Strategy

## Purpose

Use this reference when the user's background is incomplete, scattered across materials, or missing experiences that have not yet been recognized as resume-worthy.

The goal is not to force the user through a giant form. The goal is to gradually build a reusable background profile with enough structure to support JD analysis, resume tailoring, gap diagnosis, and interview preparation later.

Core principle:

Do not only ask what projects the user has done. Help the user identify which past experiences are worth turning into reusable project evidence.

## Intake Principles

- Start from existing materials first.
- Extract obvious facts before asking new questions.
- Do not force fixed target roles too early.
- Do not assume the user can accurately classify all useful past work as "projects".
- Prefer multiple short rounds over one large questionnaire.
- Separate confirmed facts, tentative materials, and unknowns.
- Treat unfinished but meaningful work as candidate evidence until proven irrelevant.
- Explicitly probe for experiments, comparisons, and validation work.
- For internships with multiple responsibilities or role shifts, store base facts separately from role-specific narrative versions.
- Build version 1 early, then iterate.

## Intake Stages

### Stage 1: Extract the Obvious Facts

Start by reading any existing materials the user already has, such as:
- old resumes
- portfolio sites
- project links
- Figma links
- GitHub links
- public posts or creator pages
- screenshots, reports, or structured notes

At this stage, only extract the obvious:
- basic identity information
- education
- internships and work experience
- already-documented projects
- explicitly listed tools and skills
- visible links and evidence

Rules:
- Do not immediately rewrite or rank everything.
- Do not pressure the user to choose their "best" projects yet.
- First build the skeleton.

### Stage 2: Probe Hidden Experience From Multiple Angles

Once the obvious facts are extracted, look for missing but potentially valuable experience.

Do not ask only:
- "What other projects have you done?"

Instead, probe from multiple angles.

#### Angle A: Internships and work
Ask about:
- role changes
- side responsibilities
- cross-functional work
- experiments
- coordination work
- operational tasks that later turned into product work

#### Angle B: Competitions, programs, and training
Ask about:
- competitions
- bootcamps
- creator programs
- training camps
- PM camps
- startup or incubation programs
- any program where the user produced an output, even without winning

#### Angle C: Self-built work
Ask about:
- websites
- demos
- prototypes
- tools
- automations
- skills
- agents
- workflows
- mini apps
- MVPs built for a personal pain point

#### Angle D: Content and operations
Ask about:
- content channels
- video projects
- scripts
- editorial workflows
- platform operations
- creator collaboration
- KOL work
- distribution and performance review

#### Angle E: Problem-solving and workflow improvement
Ask about:
- repeated problems the user solved for themselves or for a team
- processes they standardized
- docs, templates, trackers, or systems they designed
- work they did that improved coordination, efficiency, or clarity

#### Angle F: Experiments and validation
Ask about:
- A/B tests
- strategy comparisons
- alternative方案验证
- manual vs automated process comparisons
- conversion tests
- pricing or incentive validation
- any case where results changed the next decision

Important rule:

A user may have done valuable work without recognizing the formal label for it. Probe for equivalent experiences, not just for textbook terms.

### Stage 3: Standardize Experiences Into Reusable Entries

Once candidate experiences are identified, normalize them into reusable profile entries.

For each experience, try to collect:
- time
- context or background problem
- the user's role
- tools used
- key actions
- outputs or results
- any metrics or directional outcomes
- evidence materials
- likely role relevance

The goal is to convert:
- vague memories
into
- reusable profile components

At this stage, do not over-polish the writing yet. Focus on completeness and retrieval value.

### Stage 4: Confirm Strengths, Boundaries, and Narrative Flexibility

Once enough material exists, confirm how it should be used later.

Clarify:
- which experiences are strongest
- which experiences are weaker but still useful
- which unfinished projects should stay in the profile
- which experiences should not be overstated
- which roles or responsibilities belong to the same internship but need different narrative versions
- where evidence is still weak
- what is factual versus inferred

This stage is about future safe reuse, not just current summarization.

## Required Fields vs Optional Fields

### Required Fields

Try to capture these before ending the first-pass intake:
- name or identity label
- education background
- at least one real experience
- at least one reusable project or experience entry
- a basic tools/skills snapshot
- at least one evidence source if available

### Optional Fields

These can be added later:
- current role interests
- exact target job families
- all links and assets
- complete metrics for every project
- complete narrative preferences
- refined strengths summary

Important rule:

Do not block profile creation just because the user's job targets are still fuzzy.

## Hidden-Experience Prompt Bank

Use these prompts selectively. Do not dump all of them at once unless the user prefers a full intake.

### Competitions and programs
- Have you joined any competitions, bootcamps, creator programs, PM camps, or training programs?
- Even if you did not win, did you build a full proposal, prototype, or project there?

### Self-built work
- Have you built any websites, tools, automations, agents, skills, demos, or prototypes for yourself?
- Did you ever build something just to validate an idea or solve a personal pain point?

### Content and operations
- Have you run content workflows, creator collaborations, or platform operations work?
- Have you created videos, scripts, channels, or repeatable content systems?

### Problem-solving
- Have you built a system, template, workflow, or tracker that solved a repeated problem?
- Have you improved coordination, documentation, or efficiency for yourself or others?

### Experiments and validation
- Have you compared two strategies, two incentives, or two versions of a process?
- Have you run anything similar to an A/B test, even if you did not call it that?
- Did any test result change what happened next?

### Weak-but-maybe-useful work
- Is there anything you spent a lot of time on but currently feel "doesn't count" as a project?
- Did you abandon any idea only after learning something important from trying to build it?

## Experience Layering Handoff

Once enough candidate experiences are collected, pass them into the layering step.

At minimum, prepare to classify experiences into:
- core projects
- backup high-potential projects
- exploratory projects
- supporting experiences

Do not fully define layering rules here. Use:
- [project-layering-rules.md](project-layering-rules.md)

If intake is happening because of a specific JD instead of general profile building, the next step after layering is usually:
- [jd-analysis-output-template.md](jd-analysis-output-template.md)

## Successful Intake Output

A successful first-pass intake should usually produce:
- a background profile summary
- a list of missing information
- a first-pass experience map
- candidate narrative versions for complex internships
- a short list of experiences that need better evidence or more detail
- a list of experiences that may become more valuable under specific JDs

The intake does not need to be perfect to be useful.

## Common Mistakes

- asking for target roles too early
- only asking for "projects"
- assuming unfinished work is irrelevant
- treating the user's uncertainty as evidence of low value
- missing experiments because the user did not label them as experiments
- flattening internships with multiple responsibilities into one vague summary
- trying to fully polish the resume before the profile is complete
- blocking progress because some metrics are still unknown

## Escalation Rules

Ask follow-up questions when:
- an experience seems important but lacks role, scope, or result
- the user is unsure whether something counts
- an internship includes multiple distinct responsibilities
- an experience may map strongly to a JD-relevant capability but is under-described
- the evidence exists but has not yet been framed clearly

Do not keep digging forever.

Stop intake and move forward when:
- there is enough information to build a first reusable profile
- the strongest experiences are identifiable
- likely backup and exploratory materials are visible
- the missing items can be captured later without blocking current progress

Build version 1 early, then refine in later JD cycles.
