# Project Layering Rules

## Purpose

Use this reference to classify the user's experiences into reusable layers before JD tailoring.

The goal is to avoid treating every experience as equally important. A layered experience map makes it easier to:
- prioritize the strongest evidence
- keep useful but weaker materials available
- preserve unfinished work without over-promoting it
- dynamically re-rank projects for different JDs

Core principle:

Not every experience should be treated equally, but unfinished or indirect work should not be discarded too early.

## Layer Definitions

### Core Projects

Core projects are the strongest reusable proof assets.

A project is usually core when it has most of the following:
- a clear background problem
- a defined role
- concrete actions
- visible outputs or results
- evidence that can be explained or shown
- strong relevance to multiple likely JDs

Core projects are the default pool for resume tailoring, but they are not the final project order.

### Backup High-Potential Projects

Backup high-potential projects are useful, relevant, and often impressive in the right context, but they are not default lead evidence.

A project is usually backup high-potential when:
- it has a real problem and meaningful work
- it has some output or product shape
- it may be highly relevant to specific roles
- it is slightly weaker than core projects in completeness, impact, or evidence quality

These projects can move up when a JD makes them especially relevant.

### Exploratory Projects

Exploratory projects are not mature enough for default use in the main resume story, but they still have evidence value.

A project is usually exploratory when:
- it was unfinished
- the MVP did not work well
- the direction was abandoned
- the user does not consider it polished
- but it still shows problem definition, validation effort, technical blockage discovery, or useful reflection

Exploratory projects are often useful for:
- backup storytelling
- interview discussion
- showing curiosity, initiative, and product thinking

Unfinished does not mean useless.

### Supporting Experiences

Supporting experiences are not core project assets, but they strengthen credibility or explain where certain work came from.

These often include:
- training camps
- creator programs
- competitions with limited outputs
- certifications
- contextual experiences that support a stronger project

Supporting experiences usually stay later in the resume and rarely drive the main story on their own.

## Layering Criteria

When deciding a layer, evaluate the experience across these dimensions:

- problem clarity
- role clarity
- action specificity
- output existence
- evidence strength
- result quality
- JD transferability
- user confidence in explaining it
- narrative usefulness

Important rule:

Layering should not be based only on polish. It should be based on evidence value and future usefulness.

## Promotion Rules

A project can move up a layer when:
- a later JD makes it highly relevant
- more metrics, links, screenshots, or outputs are added
- the role and actions become clearer after follow-up questions
- the project turns out to prove a capability more directly than an existing core project
- the user gains better narrative confidence and supporting detail

Examples:
- a backup project becomes core for an AI product JD
- an exploratory project becomes backup after its problem, role, and evidence are clarified
- a process/workflow project rises once its product logic becomes explicit

## Demotion Rules

A project can move down a layer when:
- it is weakly related to the current JD
- evidence is too thin to justify prime placement
- it consumes space better used by stronger experiences
- the user strongly dislikes using it as a flagship story
- it risks weakening an otherwise focused role narrative

Important rule:

Demotion in a specific JD does not mean permanent demotion in the master profile.

## Handling Unfinished Work

Do not discard unfinished work too early.

If a project is incomplete, still ask whether it proves:
- a real problem was identified
- a user need was hypothesized
- a product or solution was attempted
- constraints or technical blockers were discovered
- conclusions or reflections were formed

An unfinished project may still belong in:
- backup high-potential
- exploratory
- interview-only material

Use caution:
- do not present unfinished work as mature product evidence
- do not inflate weak MVPs into successful launches
- do preserve useful learning and product judgment

## Multi-Role Experience Handling

Some internships or work experiences contain multiple real narrative paths.

When this happens:
1. record the base facts once
2. separate distinct responsibility tracks
3. create narrative versions
4. tag which JD types each version fits
5. choose one main narrative version per tailored resume

Examples of narrative version differences:
- product assistant version
- growth/product-ops version
- KOL operations version
- strategy/growth version

Do not flatten all responsibilities into one vague block if that makes the story weaker.

Do not over-split either. The goal is usable narrative flexibility, not fragmentation.

## JD-Driven Project Ranking

Layering is not the same as final ranking.

When working on a specific JD:
- start from the layered pool
- re-rank by JD fit
- allow backup high-potential projects to outrank core projects when justified
- use supporting experiences only when they strengthen credibility
- avoid using too many projects in the main story

The final ranking should answer:
- what best proves fit for this specific role
- what should lead
- what should support
- what should stay out

Project ranking should change across different JD types.

For the actual JD-analysis output structure, use:
- [jd-analysis-output-template.md](jd-analysis-output-template.md)

## Output Requirements

After layering, the system should usually be able to produce:
- current core projects
- current backup high-potential projects
- current exploratory projects
- current supporting experiences
- projects that still need stronger evidence
- projects that may rise for specific role types
- internships that require multiple narrative versions

This output should be stable enough to support later JD-specific reranking.

## Common Mistakes

- treating all experiences as equally important
- using personal preference instead of JD relevance
- discarding unfinished work immediately
- keeping project priority fixed forever
- confusing supporting experiences with flagship proof assets
- failing to split multi-role internships into usable narrative versions
- over-promoting a project just because it feels creative
- underestimating workflow, system, or process projects that may be highly relevant in some JDs

## Escalation Rules

Ask follow-up questions before final classification when:
- the user spent significant time on something but thinks it does not count
- a project seems weak but may contain strong hidden evidence
- a role shift inside an internship changes the likely narrative
- a backup project may actually be the best fit for a target JD
- a project has actions but lacks visible results
- a project has results but unclear ownership

Move forward once:
- the strongest evidence pool is visible
- weaker but useful materials are preserved
- complex internships have narrative versions
- enough structure exists to start JD-specific ranking

The goal is not perfect taxonomy. The goal is reliable reuse.
